# Every player uses the protocol view

Every kind of player, including the browser and future bots, talks to the authoritative server through the wire protocol and the hidden-information-safe `PlayerView`, never through engine functions. This decision, settled in [spec #76](https://github.com/Scott-Poole/card-game/issues/76), gives all players the same information and action boundary instead of giving bots privileged engine access. Rule knowledge shared by the engine, protocol and clients lives in the small rules module so a client can assess legality from its view without full match state.

## Consequences

A bot is a protocol client that can run in-process or over a socket. Its decisions use the same view and messages as the browser; running beside the server does not grant access to engine state or opponent secrets. The server owns engine calls and remains authoritative even when a client has checked legality locally. This player boundary is a design requirement checked in review; current lint rules do not prohibit all client-to-engine imports or distinguish a future in-process bot from the server host.

The player-facing contract is `PlayerView` in `src/protocol/messages.ts`; the engine declares a separate, structurally parallel `PlayerView` for its server-side projection. Seats are identified by `PlayerId` (`0 | 1`) and the view's `player` field; the internal `Seat` record in `src/server/match.ts` associates that side with its match.

## Implementation snapshot (2026-11-16, base a038f1f)

- `src/protocol/messages.ts` defines `ClientMessage` (`join`, `stage`, `commit`), `ServerMessage` and the wire `PlayerView`, which carries the match's three lane locations (`locations`, in lane order) for both players, and each player's three face-up off-board `zones` (destroyed, discarded, banished) in full for both sides. Its `PlayerId` (`0 | 1`, declared in `src/rules/index.ts` and re-exported here) identifies the view's `player`; `src/engine/index.ts` declares a separate, structurally parallel `PlayerView`. The internal `Seat` record in `src/server/match.ts` holds a match and player side; the host maps each peer to its seat.
- `src/engine/index.ts` owns full `MatchState`, projects each player's information with `playerView`, and applies player actions through `applyAction`. These are server-side interfaces, not player entry points.
- `src/server/match.ts` implements `matchHost`, with injectable seed and decks. Its returned host pairs queued peers or seats two peers directly through `start`, applies actions and sends each peer its own projected `state` message. `src/server/direct-match.test.ts` exercises direct seating.
- `src/server/scripted-player.test-support.ts` exports the test-only `scriptedPlayer`, which imports only protocol and shared rules and chooses actions from its view. `src/server/scripted-match.test.ts` drives full matches through the host's protocol messages, checking results and hidden-information safety.
- `src/client/store.ts` owns the browser protocol connection through `connect` and outgoing actions through `send`. It decodes incoming messages and dispatches views to `matchSlice` in `src/client/matchSlice.ts`. `src/client/App.tsx` routes the screens; `src/client/ProtocolGame.tsx` provides the default export `ProtocolGame`, which renders match play from the protocol view in Redux and sends join, staging and commit messages.
- `src/rules/index.ts` supplies shared rule constants, the closed `LocationEffect` union, the pure `checkStaging` and `legalPlays` helpers over a structural view, and the shared `PlayerId`, `Play` and `opponentOf`. Engine, protocol and browser code already import this module.
